Three laws that shape everything downstream

These are not aspirations written in a README. Each is enforced by code and asserted by the test suite, and each one rules out a whole class of design that would otherwise be tempting.

Law 1

The query path never calls out.

No /api/* route issues an outbound request. The alternative — fanning out to sixty marketplaces when a user types — was measured at a p95 of 2.8 s for plain HTML and 8.0 s for JS-rendered pages, against a 200 ms budget. That is 84× over, and two orders of magnitude is not a tuning problem, it is a different architecture. So collection is a scheduled job and search reads only what is already on disk.

Enforced rather than promised: lib/no-network.ts replaces globalThis.fetch on the request path with one that throws and records the URL, and a test proves it fires.

Law 2

Every displayed price carries a unit basis and a freshness timestamp.

The <Money> component cannot be called without a unit, and a card cannot render without {unit, delivery_scope, gst_treatment, priced_as_of, freshness_state}. There is deliberately no code path that puts a bare rupee figure on screen — “₹340” with no basis is the single most common way a price comparison misleads.

Law 3

The price search shows is the price the cart would bill.

One function, resolvePrice() in lib/price.ts, is the only code permitted to state a rupee figure. The search card, the detail sheet, the vendor table and the list total all call it, and the tests assert they agree to the paise. A second pricing path is how the number on the card and the number at checkout drift apart.

End to end, in one view

Data moves in exactly one direction. The left column below is a real sequence — each stage consumes only what the stage above it produced, which is what makes any figure on screen traceable back to the HTTP response that carried it.

01

Collection — and the discipline of recording every refusal

enters a category and a city → leaves RawOffer[] + one SourceResult per source

Six adapters implement a single interface. Each declares which (category, region) pairs it can serve, and the runner walks pass → adapter → category → region until two consecutive passes surface nothing new.

AdapterClassWhat it reaches
indiamartb2b_directoryThe long-tail dealer supply for both cities. Seeded slugs plus a crawl frontier that discovers sibling categories. Produces most of the volume.
exportersindiab2b_directorySlug vocabulary with real pagination, driven by a record count the page publishes about itself.
platformsplatformRegional retail platforms, a small fixed target list.
directoriesb2b_directoryTradeIndia and Justdial, on a tolerant generic parser.
tgpredgovernmentTelangana PRED monthly rate circulars — the government reference line.
assistedmarketplaceReplays typed browser-assisted captures for sources that refuse a scripted client.

Politeness is a budget, not a courtesy

The fetch layer keeps a per-host gap and widens it on a 429, tripping a circuit breaker rather than hammering. This matters more than it sounds: IndiaMART throttles on volume, and because the runner walks Hyderabad before Vijayawada, a category with deep Hyderabad stock can spend the whole per-host window before the second city is ever asked. That reads in the data as “Vijayawada has no supply” when it means “we never got to ask.” A --region= flag exists to put the starved city first — though it cannot reset the budget, because the throttle is wall-clock per host and a fresh process inherits the window the last one left behind.

Eight outcomes, and why the distinction earns its keep

Every attempt records an outcome and an estimate of the volume behind it. The vocabulary is ok, blocked, rate_limited, login_wall, captcha, parse_fail, empty, skipped.

A defect this actually caught

empty and parse_fail look like the same thing and are not. ExportersIndia was answering with a 503 KB page carrying 108 listings, and the shared parser extracted zero — its container selector matched nothing, and its price regex required a ₹ glyph that does not exist in the rendered text because the rupee sign on that site is an <img>. Reported as empty, that read as an absent market for the entire build. Reported as parse_fail, it reads as our bug. The source now yields real supply.

The run headline used to count only ok and the blocked family, so empty, parse_fail and skipped rows were attempted and then vanished from the arithmetic. It now prints every outcome and asserts they sum to the number of sources attempted.

The archive is the thing that makes parser changes cheap

Every RawOffer is appended to collector/raw/<source>-<date>.jsonl before normalisation. That has two consequences worth the disk space. A rule change — say, discovering that a brand roster was resolving a district name as a manufacturer — can be replayed against the archive with zero network calls via scripts/rebuild-from-raw.ts. And any figure on screen can be traced back to the exact text the source published. Archived HTML bodies in collector/fixtures/ go further still: a parser can be proven end to end, including whether its rows survive normalisation, before a sweep is spent finding out.

02

Normalisation — where most of the honesty lives

enters one RawOffer → leaves a typed product + a canonical price, or a stated reason for refusing

This is the stage that decides whether two listings are the same product, what unit a price is really quoted in, and which claims are supported. It is also the stage most able to do quiet damage, so it is built to fail loudly.

Gate 1 — is this even the category it was filed under?

A cement directory page links to waterproofing compound, tile adhesive and mortar. A pipe page links to conduit and column pipe. Each category carries a rejection pattern, and a listing whose title names a different product class is refused with that reason recorded — not filed under the wrong heading to inflate a count.

Gate 2 — brand resolution, ranked by evidence

Brands are matched against a hand-verified roster, longest match first, in three tiers of evidence: the listing title, then the seller’s brand field, then the spec blob. Two rules earn their complexity:

  • Cement is rostered by product line, not parent company. “Birla” is four different companies’ brands — MP Birla Samrat, Birla Shakti, Birla Gold, Birla A1. Collapsing them to one token merged four products into one whose floor price belonged to whichever was cheapest.
  • A name that only ever appears inside another name stays out. Hindware occurs only within “Truflo by Hindware”; since matching is longest-first, adding it would relabel Truflo’s own pipes as Hindware’s.
A place is not a brand

Karimnagar and Karnataka were once roster entries, so “Clay Rectangular Karimnagar Red Bricks” resolved to brand Karimnagar — and a Telangana district became the single largest brick brand in the catalogue, ahead of every real manufacturer. A place of firing is not a maker. Both were removed and those listings now carry no brand, which is what the source actually supports. The qualified kiln names stay, because “Karimnagar ABN Bricks” is a seller’s product name and the trade genuinely identifies kilns by their initials.

Gate 3 — the canonical unit, per category

Prices are only ever compared on one basis. Conversions are a table with tests, never arithmetic, because the trade’s inch-to-millimetre mapping is not arithmetic: 1″ CPVC is 25 mm nominal bore, but 4″ SWR is 110 mm outside diameter. Multiplying by 25.4 gets both wrong.

CategoryCanonical unitWhy that one
Cementone 50 kg bagThe standard sale unit under LMPC Rule 3(a). A 25 kg pack is rescaled ×2, a 1 kg pack ×50.
TMT steelkgSold by weight; length is a spec, not a basis.
Water pipesrunning metreA 3 m pipe and a 6 m pipe cannot share a price band.
Bricks & blockspiece₹/1000 ÷ 1000; ₹/m³ × the unit volume derived from its size.
Why “50 kg” is load-bearing

bag was once treated as dimensionless, so a per-bag quote passed through unscaled — and a ₹150 quote for a 1 kg pack of Birla White became ₹150 per bag, the cheapest cement in Hyderabad and the top result for cement. Every cement price now goes through a single function that lands on the 50 kg basis, which pushes novelty packs past 10× the category median where the absurdity gate quarantines them.

Refusing is a first-class outcome

When a unit cannot be mapped, the offer is not loaded and the reason is counted. Real examples from the last sweep: unmappable unit "8000 pieces", cannot convert ₹/kg to ₹/piece without inventing an attribute, quoted per sqft — needs a wall-thickness assumption we will not make. Every one of those is a listing the system could have published with a plausible guess, and did not.

The missing-data ladder

Not every field is known, and pretending otherwise is the failure mode. Each field lands on one of four rungs, and the rung is shown to the reader rather than hidden:

RungMeaningHow it renders
quotedThe seller published itPlain, no qualifier
derivedComputed from something they did publishLabelled, with the arithmetic one tap away

unknownNobody knows“Not published by seller”, with a link to the page

Entity resolution — the identity key

A product’s identity is a hash of the attributes that actually distinguish it: brand, plus the per-category discriminators (cement type and grade; pipe system, bore and pressure class; block type and size). When the required attributes are missing, the listing gets an UNRESOLVED:<source_ref> key — one product per offer — rather than being merged into a neighbour on a guess. Under-merging costs a slightly higher product count; over-merging publishes the wrong floor price, which is worse.

03

Load — one transaction, stable keys

enters normalised rows → leaves committed vendor / product / offer rows

Identity is derived, never auto-incremented, so a re-run updates rather than duplicates: 

offer_id   = hash(source_id | source_ref)   ← stable across rebuilds
product_id = hash(item_code)               ← re-keys when resolution rules change
vendor_id  = hash(platform | name | locality)

That offer_id being stable is what lets price_history survive a full offline rebuild: the ledger is append-only and its rows carry the offer id, so re-deriving every product from the archive re-keys product_id without orphaning the history. The discontinuity is reported and written to a diff log rather than left as silent dangling keys.

Vendor geocoding resolves a locality against a shipped 213-row pincode table with coordinates. Where it cannot resolve, the fallback distance is derived from a hash of the vendor id — identical on every page load and every refresh, because a delivery cost that changes when you reload destroys the product’s credibility.

04

The price surface — integer paise, all the way down

enters offers + a destination region → leaves offer_price and price_current, materialised

Every figure is integer paise. No float touches a rupee anywhere, because a cart total that differs from the sum of its lines by a rupee is a dispute on a signed contract, and floating-point rupees produce exactly that at scale. Even parsing is integer-safe — rupee text is read as two integers rather than multiplied as a decimal, so "8.70" becomes 870 paise and never 869. 

landed     = base_ex_gst + gst + freight + handling + loading
normalised = landed per canonical unit   ← the number ranked, filtered and banded on

Freight is deterministic, and shows its working

Distance band (vendor locality → your pincode) × chargeable weight (the greater of actual and volumetric) × vehicle class (parcel / tempo / LCV / 6-tyre / 10-tyre) × a category minimum, with free-delivery thresholds where a vendor publishes one, amortised across the seller’s MOQ. Never random, never re-rolled. Every figure renders with an estimated badge and a one-tap breakdown containing the arithmetic.

GST is effective-dated, not a constant

Rates are stored per HSN and category with an effective-from date and a citation, so a historical price is reconstructed at the rate that applied then rather than the rate in force today.

The absurdity gate

Before publication, every normalised price is checked against the median for its category. Anything outside [0.1×, 10×] is quarantined and never published, with the ratio and the offending key printed in the run log. On the last sweep it caught 25 — a ₹3,922 “brick” at 109× the median, among others. This is the last line of defence against a unit-conversion error reaching a buyer, and it is deliberately loud rather than silent.

Two tables, because a product price and a seller price are different things

  • price_current — one row per (product, region): the floor price and the offer count, for banding and comparison.
  • offer_price — one row per (offer, region, tier): what this seller charges. This is what the results list actually ranks, now that a card is a vendor rather than a product.
05

Retrieval, faceting and rank — 14.9 ms with no network hop

enters a typed query + pincode → leaves ranked vendor cards + live facet counts

Parsing what a builder actually types

The query grammar extracts typed constraints rather than treating the query as a bag of words: 8mm tmt yields a diameter, 4 inch cpvc a bore and a pipe system, 53 grade a cement grade. It handles trade vernacular (sariya, ఇటుక), fraction glyphs (½"), and misspellings within an edit distance of two — so ultratec reaches UltraTech.

Two retrievers, fused

FTS5 for lexical matching and a trigram index for fuzzy matching, score-normalised and fused. sqlite-vec was deliberately not added: the measurement came first, and lexical plus trigram already answers the golden query set at 6.6 ms p95. A vector index would have added a dependency and a build step to a stage that is not the bottleneck.

Nine ranking features, disclosed as they are applied

#FeatureWeight

There is no order history in this build, so f8 is honestly zero and its weight is redistributed to relevance and price rather than left as a phantom term. Seller ratings are shrunk toward the mean by review count, so a single five-star review does not outrank a hundred four-star ones. The labels above are exactly what the interface prints under “Sorted on”, because CP (E-Commerce) Rule 5(3)(f) requires the ranking parameters you disclose to be the ones you apply.

One card per vendor

The results list is seller-led: ranking happens over offers, then offers collapse to one card per vendor with a “+N more from this seller” roll-up that keeps every source URL reachable. Crucially the grouping is applied after scoring and after facets, so a filtered view still shows distinct sellers top to bottom rather than the same seller repeated.

Making 19.5 ms happen

Two rounds of optimisation, both triggered by work repeated in an inner loop, and both worth naming because the fix was never to relax the target:

  • Facet labels were re-parsed per row; they now compile once per request. Faceting 16.84 → 3.33 ms.
  • Going offer-level meant JSON.parse on each row’s attributes per facet — roughly 8,000 parses a query. Parsed attributes are now memoised on the row, and display columns are fetched only for the 24 rows actually rendered. Query layer 26.04 → 15.57 ms.

A readable reference implementation of the comparison is kept alongside the fast path, and a test decides every (row, facet, value) triple both ways and asserts they agree — an optimisation that silently changed a count would be a worse defect than the latency it fixed.

The zero-result ladder

A query that matches nothing never returns a blank page. Constraints are relaxed in a defined order — the most incidental first — and the interface states which constraint it dropped and offers to restore it. The relaxation order is part of the grammar, not an afterthought.

06

Filters — reconciled against the catalogue that exists

enters authored filter trees + real aggregates → leaves filters/*.json and a re-seeded facet_definition

The four filter trees were designed before any data existed, so their brand rosters, price bands and counts began as illustrative. Reconciliation rewrites all three from measured aggregates: brand values become the brands actually collected, ordered by result count, and price bands become quartiles of the real distribution rather than round numbers — ₹0–500 / ₹500–1000 on a catalogue whose middle half of cement bags falls between ₹350 and ₹420 gives you one useful band and three empty ones.

A facet with nothing behind it ships disabled, never deleted

The gap stays visible. And the reason distinguishes two different facts that a single disabled pill would conflate:

  • Uncollected — nobody publishes it. Bulk pricing slabs: 0 of 1,755 offers declare a quantity break.
  • Unnormalised — everybody publishes it, as prose. Cement application is populated on 124 of 627 listings, as “Construction”, “For Construction”, “Used For Constrution” — free text matching none of the five authored values. The data is there and an extractor would reach it; that is a different backlog item from a collection gap, and the reason string now says which.
Disclosed must equal applied

The query layer reads facet_definition; the JSON trees are what that table is seeded from — but only database initialisation ever seeded it. So reconciliation rewrote four documents and left the running rail on whatever was seeded last. Visibly: the published cement tree said Under ₹350 / ₹350–₹380 / ₹380–₹420 while the interface rendered Under ₹320 / ₹320–₹380 / ₹380–₹440. Disclosed parameters that are not the applied ones is precisely what CP (E-Commerce) Rule 5(3)(f) prohibits. The seeding now runs as the last step of reconciliation, so the two are written by one command and cannot drift.

07

The interface — “Alabaster”

enters ranked cards + facet counts → leaves a painted frame inside 200 ms of the keystroke

One canvas, no light/dark toggle: a warm ivory ground with a soft colour wash, white frosted glass surfaces, deep charcoal text and a single enriched copper accent — the colour of brick leaving the kiln. The rule that makes it work is that the accent is spent once per view, on the unit price.

Blur is rationed, and that is a performance decision

backdrop-filter is not free. Blurring 24 result cards plus a virtualised vendor table plus a sticky rail puts real GPU cost on every scroll. So blur goes only on a few large persistent surfaces — top bar, filter rail, detail sheet, compare tray, search dropdown — while the many repeated cards use a non-blurred translucent white with an inner highlight. Over a near-flat canvas the two are visually indistinguishable, and blur on everything reads as mush anyway.

Legibility is the product

This is a page of prices, so every foreground/background pair was measured against the composited background — the colour after alpha blending, not the token — and anything under 4.5:1 was darkened until it passed. Two values needed it. Translucent panels under dense figures are the classic way glass interfaces fail.

Pictures answer attention

Each card carries up to five photographs and rotates them only while the cursor is on it, returning to the first frame when attention leaves — twenty-four cards animating at once is a fairground. Frames two through five are not in the DOM until first hover, so a page load fetches 24 images rather than 120. Every picture is downloaded locally, so viewing a card makes no third-party request and the demo works offline. Deduplication is keyed on the image path with its size suffix stripped, because the same photograph served at five widths is one picture, not five.

The last supply fix broke the budget, and the budget won

Those are the best numbers in the build, on the largest catalogue in the build — and an hour earlier the same benchmark failed. Adding the ExportersIndia supply took the query layer to 21.56 ms p95 against a 20 ms target, with cement at 22.66 ms. Nothing had regressed; every stage was simply in proportion to a catalogue that had grown from 306 products to 912.

The target was not moved. The fix came from noticing what the slowest stage actually was: fetch — reading the candidate set out of SQLite — was 7.17 ms of it, and that set only changes when the price surface is rebuilt. Search never writes. So it is now read once per (region, category) and reused, keyed on PRAGMA data_version, which SQLite bumps whenever another connection commits — so a collection run in a separate process invalidates the cache without needing to signal the web process. A wall-clock TTL would have served a stale catalogue for its duration; an in-process counter would never have seen the collector at all.

Sharing rows across requests is sound here for a specific reason: the only thing ever written to a row is that memoised attribute parse — idempotent, and now paid once for the life of the catalogue instead of once per request. Query layer 21.56 → 14.94 ms, cement 22.66 → 15.78 ms. And because a cache is only worth having if it is invisible, the suite runs one query cold, warm and after a flush, and asserts all three return identical offers, prices and facet counts.

What is honest about the data

Collection ran against real sources and recorded every refusal. Nothing was capped silently and no offer was ever invented. Three limitations are worth naming because they shape what the demo can claim:

  • The platform floor is the one guardrail still unmet. The target is four independent platforms per category. Amazon, Flipkart, Meesho, JioMart, Moglix, BuildersMART and Infra.Market each refuse a scripted client with a browser challenge or a JS wall — recorded with an estimate of what sits behind each. Breadth is limited by what can be reached politely, and the shortfall is reported rather than papered over by counting one platform twice.
  • The Telangana government circulars are scanned images. The monthly series resolves and downloads correctly, but it is 1.5 MB of JPEG streams yielding 23 characters of extractable text. The document is cited as the reference line with its month and URL; the rupee figures inside were not machine-extracted and none was invented from them. Reading them needs OCR.
  • Andhra Pradesh publishes no current Schedule of Rates. The newest verifiable edition is 2018-19, so Vijayawada has no in-state government anchor and the Telangana series is shown to it as an explicitly cross-border cross-check.

A fourth is a matter of reading: ExportersIndia sellers frequently quote a range. A listing reading “Rs 24 – Rs 28 per piece” is stored at ₹24, with the full range kept verbatim and the original string preserved. The low bound is a figure the seller actually printed; a midpoint would not be. Read the ranked price on those rows as “from”.

BuildO Price Intelligence runs entirely on one machine — one SQLite file, one Next.js process, one scheduled task. Nothing touches the cloud, including the fonts, which are downloaded at build time and self-hosted. Figures on this page are from the working dataset and move with each sweep; the coverage script is the source of record for all of them.
